## 架构约定
```text
src/core/
├── publish.ts        # 跟随 vault 站点的站内路径 = vault 路径；挪动（moveNote / 批量）：删旧路径、写新路径、旧路径记入 aliases
├── status.ts?        # 「已移动」判定并入 noteStatus：跟随 vault 站点 record.sitePath ≠ vaultPath
├── companions.ts     # （自 Phase 3 移入）连带收集：一层 / 到底，去重防循环，跳过排除 / 已发布 / 仅嵌入
├── renames.ts        # vault 改名 → manifest 源路径更新（纯逻辑：old→new 映射应用到 manifest）
└── transform/        # 发布副本 frontmatter 写入 aliases（不受白名单限制，与笔记自带 aliases 合并去重）
src/ui/
├── actions.ts        # 「全部站点」；跟随 vault 站点的发布流程；连带清单；改名监听
├── publish-modal.ts  # 多站首次发布：按站点分块（手动块 = 目录 / 名称；跟随块 = 固定 vault 位置），含双链处理三选一
└── companions-modal.ts # 连带清单：勾选、位置（= vault 位置）、冲突标记
src/settings/         # 目录模式切换：写回仓库 manifest；手动 → 跟随时确认清单
```

## 详细实施步骤

### Phase 4-1: 跟随 vault 模式与模式切换（需求 §5.1、§5.2、§9）
#### 具体任务
- 跟随 vault 站点：站内路径 = vault 路径（目录与文件名完全一致），首次发布不需要用户填位置
- **模式以仓库 manifest 为准**：读取快照时若 manifest 的 `mode` 与本地设置不同，以仓库为准并更新本地设置（换设备一致）；仓库尚无 manifest 时用本地设置
- 设置页切换模式 → 一次提交写回 manifest（只改 `mode`，切换本身不挪动任何内容）
  - 跟随 → 手动：直接切换，「已移动」消失
  - 手动 → 跟随：统计站内路径 ≠ vault 路径的笔记 N 篇；N > 0 时弹确认框（需求 §5.2 文案，可展开清单），确定后它们显示为「已移动」
- 模式写回失败（网络 / 权限）时设置不变并提示
#### 验收标准
- [✓] 单元测试：跟随站点路径计算、模式以仓库为准、切换只改 manifest 的 mode、N 的统计（`follow.test.ts`）
- [✓] 测试 vault 实测：两站点分别手动 / 跟随，切换确认框、切换后状态

### Phase 4-2: 「已移动」状态与挪动（需求 §6.1、§11）
#### 具体任务
- 状态：跟随 vault 站点上 `record.sitePath ≠ record.vaultPath` → 「已移动」（可与「有修改」叠加）；手动站点没有「已移动」
- 挪动（core）：删除旧路径文件、在新路径写入、旧路径写入新副本 frontmatter 的 `aliases`（旧网址重定向，需求 §11）；manifest 的 sitePath 与 aliases 同步更新；一次提交
- aliases 写入发布副本 frontmatter：不受属性白名单限制；与笔记自带 aliases（若在白名单中）合并去重；新位置与站上已有内容冲突时拒绝
- 站点未启用 AliasRedirects 时提示「挪动后旧链接将失效」
- 右键发布一篇「已移动」笔记（用户决定 A）：同步——挪到新位置并更新内容，旧路径写入 aliases；新位置冲突时拒绝并提示。批量「一键同步 / 重排」留给 Phase 5 面板复用本步的 core
#### 验收标准
- [✓] 单元测试（假 GitHub）：已移动判定、挪动一次提交（删旧 / 写新 / aliases / manifest）、挪动冲突拒绝、aliases 合并去重、批内链接指向新位置（`follow.test.ts`）
- [✓] Quartz 实际构建：挪动后旧网址重定向到新页面（`改名/待改名.html` → `改名/已改名`）

### Phase 4-3: vault 改名 / 移动监听（需求 §9）
#### 具体任务
- 先实测 `rename` 事件：单文件改名、移动到其他文件夹、文件夹改名 / 移动时的触发方式
- vault 中笔记改名 / 移动 → 所有站点 manifest 中该笔记的 `vaultPath` 更新为新路径（站内路径不变；跟随 vault 站点因此出现「已移动」）
- 写回方式（用户决定 A）：改名后自动提交；几秒内的多次改名合并为一次提交（每个受影响的站点各一次）；离线或失败时记入本地待写队列（`data.json`），下次任意操作或插件加载时补提交；只更新 manifest，不改发布内容
- 附件改名：manifest 中附件按站内路径记录、与 vault 路径无关，不受影响（内容 SHA 不变即复用）
#### 验收标准
- [✓] 单元测试：改名映射应用到 manifest（单文件、文件夹前缀、链式改名 A→B→C、互换、幂等、不相关记录不变、占用跳过）；未写回的改名参与状态与发布（`renames.test.ts`）
- [✓] 测试 vault 实测：改名、文件夹改名后自动提交「更新 1 篇笔记的源路径」，状态显示「已移动」，发布后同步

### Phase 4-4: 连带发布（跟随 vault 站点，需求 §7 2026-10-04 修订）
#### 具体任务
- 首次发布到跟随 vault 站点时，若本篇有指向未在本站发布的笔记：弹窗中「双链处理：纯文本 / 连带一层 / 连带到底」，默认取设置
- 连带收集（`core/companions.ts`）：一层 = 直接链接；到底 = 广度优先递归；去重防循环；跳过排除文件夹、已在本站发布、无法解析、仅被嵌入（不是链接）的笔记
- 连带清单弹窗：每篇显示 vault 路径（即站内位置）、冲突标记；可取消勾选（取消的变纯文本）；有冲突的不能勾选
- 本篇与勾选的连带笔记用 `publishBatch` 一次提交，批内互链正确
- 更新已发布笔记时出现新的未发布链接：按设置默认值；默认为连带时弹出连带清单确认，绝不静默多发
#### 验收标准
- [✓] 单元测试：一层 / 到底、环形链接、跳过规则、上限、更新时只收集新增的未发布链接、plainLinks 记录（`companions.test.ts`、`manifest.test.ts`）；冲突标记在弹窗中计算，GUI 验证
- [✓] 测试 vault 实测：三种处理方式、清单勾选、更新时不再询问已知纯文本链接（冲突标记未在 GUI 中构造）

### Phase 4-5: 「全部站点」（需求 §4）
#### 具体任务
- 发布 / 撤稿 / 获取链接的站点列表末尾增加「全部站点」（打开网页不提供）
- 发布 → 全部站点：已发布的站点直接更新；首次发布的站点在一个弹窗中**按站点分块**（手动块填目录 / 名称；跟随块显示固定的 vault 位置；双链处理按各站模式），一站一次提交，逐站执行并汇总结果（部分失败时列出失败站点与原因）
- 撤稿 → 全部站点：只对已发布的站点执行，一个确认框（反向链接一并更新按站点分别处理）
- 获取链接 → 全部站点：复制多行「站点名：网址」，只含已发布的站点
- 隔离站点与非隔离站点混在「全部」中时，各站点各自按隔离规则输出（需求 §8：连带不会发到用户未选择的站点）

## 实施调整记录（2026-10-04）

- **未写回的改名参与计算**：`PublishContext.renames` 在 `loadSnapshot` 中先应用到 manifest，因此改名后立即发布 / 查看状态都按新路径计算，不会把改名后的笔记当作新笔记重复发布；之后任何提交的 manifest 都已包含这些改名。改名映射幂等，Obsidian 对文件夹改名无论只触发文件夹事件、还是文件夹与子文件各触发一次，结果相同
- **改名待写队列**：`data.json` 的 `pendingRenames`（站点 id → 带递增 id 的改名列表），写回成功后只移除已写回的条目；3 秒防抖；插件加载（onLayoutReady）与每次操作时补写；提交信息只写篇数，不含 vault 路径
- **更新时「只问新出现的未发布链接」**：manifest 记录新增可选字段 `plainLinks`（跟随站点上次输出为纯文本的链接目标，为空不写入，已有 manifest 逐字节不变）。设置默认为纯文本时更新不询问
- **连带清单与三选一合并为一个弹窗**：首次发布到跟随站点、且有本站未发布链接时弹出；「到底」在选中时才遍历（上限 500 篇）；超过 50 篇再确认
- **跟随站点的发布**：core 以仓库 manifest 的 `mode` 为准（无 manifest 时用本地设置），跟随站点的站内路径一律为 vault 路径，所以「已移动」的笔记在任何发布（含反向链接的一并更新、全部站点）中都会被同步到新位置
- **全部站点**：只有手动站点需要填写位置时才弹分块弹窗；跟随站点的连带清单逐站弹出；任一弹窗取消则整体取消（此时尚未提交）。全部站点发布后暂不做反向链接提醒（单站发布保留）
- **GUI 反馈修正**：全部站点都「已是最新」时，汇总提示不再写「约 1 分钟后网站更新」
- **aliases 写法**：旧站内路径去掉 `.md`，按内容目录根解析（已核对 Quartz alias-redirects：非 `./`、`../` 开头的别名按根路径生成重定向页）

## 需要讨论（开工前请确认）

> **2026-10-04 用户决定**：第 1 项选 **A 自动提交**（几秒内合并、离线时本地排队补提交）；第 2 项选 **A 同步到新位置**（挪动 + 更新内容，旧网址经 aliases 重定向）。

1. **改名后 manifest 何时写回仓库**：
   - A. 改名后自动提交（几秒内的多次改名合并成一次提交；离线或失败时记在本地，下次操作时补提交）——多设备之间最快一致，但每次改名都会在仓库产生提交
   - B. 只记在本地，下次对该站点做任何发布 / 撤稿时随同一次提交写回——不额外产生提交，但别的设备在此之前会把这篇看成「源笔记已删除」
2. **跟随 vault 站点上右键「发布」一篇「已移动」的笔记**：
   - A. 同步：挪到新位置（写 aliases 让旧网址重定向）并更新内容——符合「跟随 vault」的直觉
   - B. 原地更新内容，「已移动」保留；挪动只在 Phase 5 管理面板的「一键同步 / 重排」中做——与需求 §5.3「再次发布 = 更新，位置在管理面板中改」一致

## 技术风险评估

### 中风险项
- **文件夹改名的事件形态**：若只触发文件夹事件，需自行推导子文件新路径
  - 缓解措施: 4-3 先实测；映射逻辑按前缀处理，单元测试覆盖
- **模式以仓库为准与本地设置的同步**：换设备、离线修改可能不一致
  - 缓解措施: 读取快照时以仓库为准并提示；写回失败不改本地
- **全部站点的部分失败**：一站一次提交，无法跨站原子
  - 缓解措施: 逐站执行、汇总结果；失败站点可单独重试

### 低风险项
- **连带到底的规模**：大 vault 中可能连带大量笔记
  - 缓解措施: 清单中显示数量，超过阈值（如 50 篇）时额外确认
